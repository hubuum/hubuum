Shared task start scheduling¶

Every successful claim commits weighted class rotation and principal service history in the same transaction as its fenced task lease. These deployment records survive logical restore. Worker availability is discarded during restore; new claims register against the reconciled control generation.

Selection and guarantees¶

Ordinary selection visits task kinds using positive integer weights, then chooses the eligible principal least recently served in that class. Ties use authoritative creation time and task ID. Retries keep their original creation time. Empty polls, failed transactions and unavailable capacity do not advance either fairness lane.

A separate promotion lane selects the oldest eligible overdue task. Its default is one promotion per eight successful claims, after five minutes of age. Promotions obey every execution cap, worker restriction and reservation. They update principal service history but do not advance ordinary rotation. A promotion requires at least the current interval since the last promotion, including after policy changes. When no overdue task is eligible, ordinary selection proceeds. An entirely overdue backlog therefore leaves at least seven of eight starts to ordinary class/principal selection with the default interval.

These are start opportunities, not CPU-time shares. With a finite eligible backlog, positive weights, recurring supporting workers and releasing capacity, each eligible principal and task receives opportunities. Permanently occupied caps, locked tasks or unsupported classes do not satisfy those assumptions. Long tasks can delay starts; the scheduler neither estimates their cost nor preempts them. Class weights describe ordinary starts. Promotions can change total start shares by at most their bounded fraction. Equal duration and equal CPU consumption are not assumed.

PostgreSQL orders principal service history before reading task queue heads, so ordinary selection can stop once the first eligible service-history tie is resolved. New principals with equal history still compare creation time and task ID. A due promotion compares overdue heads across eligible groups; an indexed check skips that comparison when no queued task is old enough. Both paths retain SKIP LOCKED, capacity checks and the same transactional scheduling counters.

Worker availability and reservations¶

Each worker loop generates one TaskWorkerId for its single execution slot and reuses it on every claim request. A request advertises a validated nonempty set of supported kinds. Built-in workers support every kind. Registration and successful lease heartbeats renew availability using the backend clock and task lease duration. A worker must finish or lose its fenced claim before claiming again. Process restarts create fresh identities; expired registrations stop contributing capacity.

Eligible capacity is the smaller of live registered slots and the configured execution-slot ceiling. A hard reservation is active only when that capacity can hold all reserved slots plus one ordinary slot, enough live workers support internal repair, and at least one supports ordinary work. Ordinary tasks cannot borrow idle reserved slots, including the last reserved internal-capable worker. Per-kind execution caps also apply to internal repair. Existing principal, collection and ordinary deployment caps remain authoritative.

A single configured slot shares execution between ordinary and internal work. It cannot guarantee prompt repair during a nonpreemptible task. The same fallback applies when the eligible pool shrinks below the reservation. Existing claims stay occupied; no task is preempted. Returning workers restore hard reservations on the next registration. Administrator snapshots derive this consistently from shared worker leases and report single_slot, insufficient_workers, insufficient_internal_workers or no_ordinary_workers. unsupported_kinds separately identifies classes with no live supporting worker.

Public diagnostics contract¶

The scheduler extends scheduling in GET /api/v1/admin/task-capacity and task_capacity.scheduling in GET /api/v1/admin/config. Both routes require an unscoped human administrator through the configured authorization backend. Ordinary users, scoped tokens and service accounts cannot inspect deployment scheduling state. The projection contains aggregate counters and task kinds, without worker identities, principal identities or other users' queued tasks.

mode is either {"mode":"reserved"} or {"mode":"shared","reason":...}. The shared reason is one of the four bounded values documented above; unsupported_kinds independently identifies kinds with no live supporting worker. Fallback does not make an unsupported kind executable. ordinary_position is a position in the scheduler's weighted rotation, not a task's queue position. Counters describe successful starts, not completed work or CPU consumption.

These diagnostics do not change the existing task response, invent per-task wait reasons, or promise queue position or ETA. A queued task remains inspectable by its authorized durable reference. Ending a client's local wait neither cancels that task nor changes its execution deadline or output lifetime.

This is the applicable #545 contract review for #507. Backend scheduling contracts cover fallback/unsupported-kind behavior; the administrator endpoint tests cover policy projection and denial to ordinary users. Broader phase/progress models, consumer helpers and provider-wait contracts remain separate #545/#516 work.

Configuration and upgrade¶

The administrator task-capacity policy now requires a scheduling object:

{
  "execution_slots": 64,
  "internal_reserved_slots": 1,
  "promotion_interval": 8,
  "overdue_seconds": 300,
  "weights": [
    {"kind": "import", "weight": 1},
    {"kind": "export", "weight": 1},
    {"kind": "backup", "weight": 1},
    {"kind": "reindex", "weight": 1},
    {"kind": "remote_call", "weight": 1},
    {"kind": "schema_validation", "weight": 1},
    {"kind": "schema_profiling", "weight": 1}
  ]
}

Slots range from 1–1,024; reservations are positive and must leave ordinary capacity when more than one slot is configured. Promotion intervals range from 2–1,024, overdue age from 1–604,800 seconds, and weights from 1–32 with each kind present exactly once. Updates use the existing revision-checked policy endpoint. Weight changes interpret the durable rotation position modulo the new rotation; service history remains intact. Reduced capacity drains existing claims first.

This is an offline upgrade. Stop API and worker replicas, take a database backup, run hubuum-admin --migrate and reconcile split-role grants, then start matching binaries. The migration creates the queued-task index and protected scheduler state and initializes the scheduling policy. Older workers cannot enforce these rules and must not coexist with upgraded workers. Retain the pre-upgrade database snapshot for rollback. Logical restore preserves fairness history but resets worker leases. Upgrade all ten storage SDK crates to 0.15 together and migrate adapters to StorageTaskClaimRequest; see the SDK guide.

Measurement¶

The acceptance profiles and P3/P4 targets are defined in lifecycle budgets. The constrained matrix below supports the eight-claim default for those workloads. A warm SQL selection probe alone does not establish end-to-end claim latency, utilization or constrained-profile acceptance.

The benchmark separates fixture preparation from measured workers. Preparation loads the checked-in lifecycle dataset, initializes immutable identity and capacity evidence, adds the requested queued backlog, and records a protected fixture marker. Worker processes reject mismatched dataset, workload, cap, reservation or overdue settings. Each process has an independent eight-connection pool and stable slot identities. The shared profile runs two processes with two slots each.

The local harness supports PostgreSQL limits of 2 CPUs/2 GiB or 4 CPUs/4 GiB and worker limits of 2 CPUs/512 MiB per process when the container runtime can enforce them. The harness verifies kernel CPU quotas and memory ceilings, PostgreSQL thread affinity when requested, and worker process RSS and high-water memory at 20 ms intervals. Five fresh database copies are measured for each of 1k, 10k and 100k queued tasks, a saturated overdue backlog, and the timed skewed-duration workload with a per-principal execution cap of one. The shared profile also runs a 90-second capacity cycle, shrinking the production policy from four execution slots to one after 30 seconds and restoring four after 60 seconds. Existing claims drain normally. Its utilization calculation clips occupancy to eligible capacity, brackets policy-commit and clock uncertainty, and prevents temporary overcommit from concealing idle time after growth. The 10k-backlog immediate runs measure 12k successful claims, leaving at least 10k ordinary selections after bounded promotions for the start-share comparison. Queued timestamps reset to the declared initial age for each fresh copy; tasks continue aging normally during the run. Immediate runs exclude a global prefix of 100 committed claims locally or 200 across the two shared processes. Timed runs complete 100 real claims per process on the same connection pools and worker identities before measuring. These warm-up claims preserve the configured caps and immediately release capacity, without simulated work delays. Their samples are retained separately, including cold-start latency; promotion spacing, query and candidate bounds still include them. The measured window uses the declared task durations and capacity cycle. Every sample, preparation inventory, container configuration and candidate-selection plan is retained. Budget failures remain in the report. A completed measurement run does not by itself certify P3/P4.

A disposable database wrapper records task index entries returned and sequential rows visited around every production scheduler call, including empty searches. Repeated visits count again; failed transactions discard their recorder rows and fail the latency check. The original function is renamed without changing its body, and its definition hash is retained. The wrapper and recorder insert remain inside measured claim latency and lock occupancy. The report requires the recorder and worker successful-claim counts to agree before checking the 1,024-entry limit. Task table and index block requests, including buffer hits, are reported separately.

PostgreSQL resource evidence includes the enforced memory.max, observed peak, and reclaim/OOM event counts. Linux permits temporary overshoot while reclaiming pages, so the peak is retained even when it exceeds memory.max; any OOM event fails verification. See the kernel memory controller contract. The worker's separate 512 MiB RSS/high-water requirement remains a strict check.

These counters include index entries returned for dead or uncommitted rows, unlike live-row plan counts; see PostgreSQL index statistics. They do not count internal B-tree comparisons, skipped entries that the index never returns, or every tuple traversed in a heap update chain. Prepared and post-workload generic plans cover all eight promotion turns. The retained counters and plans qualify the measured workload; they do not prove a universal physical-work bound for arbitrary database states.

The full scheduler acceptance matrix has 25 local and 30 shared repetitions. Run it explicitly, add the ci:scheduler label to a PR, or manually dispatch the Scheduler acceptance workflow. The label also enables reruns on subsequent pushes; removing it cancels the active run. Other labels, including ci:full and ci:benchmarks, do not enable this matrix. Normal PR CI keeps the scheduler correctness tests and harness unit tests without these timed measurements.

The opt-in workflow builds once, measures the profiles in separate jobs, and retains raw reports and build/runner metadata for 30 days even when budgets fail. It uses --check-budgets to fail after all repetitions have been recorded when P3, applicable P4 checks, or the shared database RTT limit fail. Hosted-runner hardware and contention remain part of the evidence; a green numeric check alone does not establish an equivalent dedicated deployment or a universal work bound.

Run the harness on Linux with access to the Docker host PID namespace; the 20 ms sampler reads worker processes directly from /proc. It needs permission to inspect the container processes; the CI job uses sudo for this step. On macOS, run the harness inside the Docker Linux environment with that PID namespace and use Linux release binaries. When CPU quotas are unavailable, --cpu-affinity assigns disjoint CPU masks to PostgreSQL and each worker and verifies their threads. Database and worker memory limits remain enforced and inspected:

cargo build --locked --release -p hubuum-scale-benchmark
cargo build --locked --release --features embedded-migrations --bin hubuum-admin
python3 -I -S tests/python/run.py integration scheduling-benchmark \
  --profile shared --cpu-affinity --output target/scheduling-shared

--unlimited-cpu remains available for diagnostic evidence without CPU controls. Resource enforcement does not establish SSD, RTT or candidate-work qualification. The retained plan probes and all five repetitions still require acceptance review.

PostgreSQL version compatibility¶

The latency comparison above measures commit 1350a86a before the PostgreSQL 16 compatibility fix. CI found that PostgreSQL 16 inspected 64 ordinary queue heads because it could not propagate ordering through the materialized group CTE. The group query now explicitly remains inline, preserving its ordering for the outer selection. The existing native row-read limits remain unchanged.

The compatibility plan report retains both versions of the query on PostgreSQL 16 and 18. Ordinary selection reads two task rows; a due promotion with no overdue work reads three, including the minimum-timestamp probe. All four plan scenarios pass on both versions after the fix. This verifies query plans and live-row counts; it adds no latency measurement or general physical-work bound to the earlier comparison.
