Lifecycle audit and sink-event contract¶

Proposed contract for #550, extending the shared design in #503 and public contracts in #545. The proposal is based on server commit beb37f8a.

This document specifies future lifecycle behavior. It does not enable a new event, endpoint, retention policy, or destructive operation. Feature owners must implement and qualify their applicable transitions before advertising support. Consumer review is still required; the review table below records inspected source, not consumer approval. Unrelated foundations and task/SSE work can ship independently.

Implemented protected-deletion slice¶

The offline deletion foundation implements five audit-only transitions for one exact closed object-history copy: request, access restriction, independent recovery protection, copy removal and completion. Their original identities, times and exact membership survive recovery through the protected control lineage. This introduces the lifecycle catalog entity, while subscription creation, updates and test delivery reject it. The broader transition catalog, public evidence endpoints and safe sink projection below remain proposals requiring their owning implementation and qualification.

Existing guarantees and gaps¶

Reuse the canonical event stream, AuditDocument, event catalog, audit visibility, subscriptions, delivery workers, and protected deletion authority. There is no second audit log or deletion ledger.

Catalog and versioning¶

Propose one new catalog entity, lifecycle, using the existing coarse actions below. metadata.lifecycle.name supplies the specific transition name; contract_version: 1 versions its semantics. The fully qualified event name is <name>.v1, for example lifecycle.archive.published.v1. A subscription still uses the existing entity/action validation, with an additive validated lifecycle_names filter for precise selection. An unknown name in a write request is rejected. An unknown optional reason in a read is preserved.

lifecycle_names selects fully qualified names including the major version, for example lifecycle.archive.published.v1. Lifecycle delivery requires explicit entity and name selection; legacy empty/wildcard subscriptions do not opt in. Reject empty lifecycle-name selection and audit-only names on a lifecycle subscription. A future name or major version therefore needs a subscription update and review rather than silently expanding an existing export contract.

The envelope's schema_version remains separate: lifecycle examples use version 1 with null snapshots; existing revision-aware documents remain version 2. Do not change historical event meaning or infer lifecycle completion from a generic task.succeeded event. The proposal alone activates no transition. The protected-deletion slice above uses the lifecycle catalog for audit-only facts. Further activation requires exhaustive server/adapter matches, OpenAPI, backup-reader compatibility and the consumer checks below.

Each row below is a named v1 event. Eligible means an explicit subscription may select its safe sink projection; no subscription is created automatically. Audit means audit-only, including for system subscriptions. State and audit facts commit together at the stated emission point. Repeating an unchanged transition returns its original event identity and emits nothing new.

Same-tier migration and cross-tier movement use the same archive transitions; the source and destination tiers identify which occurred. Provider preparation, pending physical deletion and cache eviction cannot be renamed as permanent expiry. Scheduled expiry uses erasure transitions under the approved policy and does not require fresh human approval for each batch.

Rejected validation, authorization and admission attempts do not emit a committed lifecycle success fact. Existing bounded security/operational logs may record them with secret-safe categories. A real provider attempt records intent and its observed outcome; retries with additional physical work get a fresh attempt identity. Polls without a state change, ordinary reads and genuine no-ops emit no lifecycle audit event. Access audit is explicitly opt-in and bounded per transfer, never per chunk. Authorization, response opening and server transfer completion prove different facts; none proves a person read, stored or retained the result. A crash can leave an access attempt without a completion fact.

Identity, authority and exact membership¶

Keep canonical event_id UUIDs and integer audit row IDs. Row IDs, timestamps and sequence allocation do not establish commit order or a global watermark. Assign an operation UUID and monotonic revision to each authorization-scoped operation; atomically advance that revision with its state and event. Retrying the same committed revision returns the existing event. Conflicting or stale claims cannot allocate a success revision. Provider attempts, execution runs and immutable batches have separate UUIDs. caused_by_event_id is optional and must point only within the same visible scope.

A root operation spanning collections remains internal. It owns separate collection operation IDs, batches and canonical events, each with its own event_id. Only an unscoped administrator may read a separate system summary. Collection events never carry the root's identity, global counts, hidden collection list or cross-scope causation. Pagination and totals operate on the authorized projection. System-only operations use a null collection and remain unscoped-admin-only. A deleted collection cannot be resolved through a reused integer ID: visibility uses stable collection identity and explicit retained audit authority, otherwise access fails closed.

Audit attribution includes the immediate actor and root initiator, stable principal UUIDs where available, trigger (manual, scheduled, recovery), policy/review references and revisions, hold/deletion generations, request correlation and causal event. Preserve the existing actor/initiator provenance; names remain permission-scoped read-time decoration. Missing historical identities are explicitly unavailable, never guessed from current integer IDs. Pin the referenced immutable policy revision and review fingerprint/scope for the evidence lifetime. A pointer to today's mutable policy cannot explain a historical decision after the policy changes or disappears. Retain those minimal authority records under the owning policy/receipt capability, without copying sensitive selector values into sink payloads. occurred_at retains the existing naive-UTC wire format and database recording semantics. observed_at is an optional RFC 3339 UTC timestamp for a separately recorded observation, not a claimed provider commit time. Neither is advertised as a transaction's commit timestamp. New monotonic revisions/generations use positive decimal strings to avoid JavaScript precision loss.

Counts alone are not sufficient membership evidence. Before moving, retiring or erasing a batch, persist a fixed, scope-homogeneous manifest of stable resource UUID/version UUID pairs and its format version, digest, bounded count and retention deadline. Store an indexed association from each pair to the manifest and event/operation UUIDs. Exact resource/version lookup must work without a live resource or original task. Catalog/segment/artifact UUIDs and configured destination UUIDs are distinct references; object keys, signed URLs, provider versions and recovery material stay private.

Audit copy references identify both source and destination configured stores and artifact UUIDs when applicable. A hot row source has null source store and artifact references; a same-tier migration retains both immutable store identities even after defaults change. Raw provider locations remain private.

Use at most 1,000 pairs and 1 MiB of encoded membership per batch. Split larger operations into independently evidenced batches; no unbounded event array. One event is at most 64 KiB encoded UTF-8, with lifecycle metadata at most 16 KiB; the safe sink envelope is at most 8 KiB. Membership pages default to 100 and cap at 250 pairs. Reject over-budget claims before I/O; never truncate a manifest and claim completeness. These are proposed initial hard limits; feature measurements must validate them against lifecycle budgets. Counters are scoped, nonnegative JSON-safe integers. Logical bytes, physically verified removed bytes and transferred bytes have separate nullable fields. Unknown physical bytes are null, never substituted with logical length or zero. Shared physical objects must not expose another scope's total size: report null unless an isolated, measured contribution can be disclosed safely.

Membership is immutable while retained. Minimum evidence contains identities, not snapshots, names, selector values or erased payload. Apply authorization, holds, minimization and erasure rules to manifests and indexes too. If identities must be removed, retire the original evidence under protected authority and return minimized; do not rewrite it under the old digest or claim exact membership is still available. A digest without retrievable authorized membership is insufficient to answer which versions were affected.

Protected minimum membership retained for the complete control lineage uses expires_at: null with retention: "control_lineage". Null never means an unknown deadline. Ordinary finite membership retains its timestamp; an optional retention: "finite" must agree with it. This represents #511's existing indefinite recovery horizon without inventing an expiry or retaining erased data.

The offline #511 administrator command is a system-only operation. Its exact membership retains the historical collection UUID, while its canonical events remain accessible only to an unscoped administrator. It does not enable lifecycle subscriptions. Trusted local administration uses a system actor and manual trigger, with no invented Hubuum principal. Older control formats explicitly report audit evidence as not recorded; an upgrade cannot fabricate past facts.

The v1 digest covers this ASCII byte stream: hubuum-lifecycle-membership-v1 and LF; manifest UUID and LF; collection UUID and LF; scoped operation UUID and LF; then one resource_uuid, TAB, version_uuid, LF line per member, sorted lexicographically by the UUID pair with duplicates rejected. UUIDs use canonical lowercase hyphenated form. There is no BOM, CR or trailing whitespace. The encoded byte count includes the header and final LF. JSON pages are views over that complete immutable manifest; a single partial page cannot verify its whole-manifest digest. The shared complete two-member example includes the matching SHA-256 and length.

Atomicity and recovery¶

Each complete backend must implement an operation-shaped lifecycle transition capability. Its validated request carries the scoped operation/revision, current claim, authority generations and required membership/verification proof. State, exact membership/index changes, canonical event and returned event receipt commit in the same transaction. Types carry validated facts across services and storage; database constraints and fencing still enforce concurrency. Ordinary append_event followed by a separate domain write is not sufficient. Failure to persist required audit evidence rolls back the transition.

Provider I/O occurs outside transactions. Commit attempt intent first; perform I/O with bounded resources; then commit verified observations under the current claim. A crash after provider success but before observation leaves a pending attempt for reconciliation, not a fabricated failure or committed success. Reconciliation reuses the attempt and immutable object identity until it proves the outcome; additional physical work uses a new attempt. Destination verified, destination published, source retired and residual cleanup confirmed are independent facts. A hold or provider lock may block a later fact without undoing earlier facts. A stale owner may report an observation for diagnostic reconciliation but cannot publish, retire or acknowledge completion.

For destructive work, #511 remains the only protected authority. Intent and required exact membership are independently recoverable before irreversible cleanup or acknowledgement that deletion started. Completion receipts must include the required audit event identities and scoped membership coverage; publish and authenticate independent coverage before acknowledging final completion. Event retention alone cannot provide this guarantee. After logical restore or supported physical recovery, quarantine exposure, recover authority, reapply restrictions and reconcile incomplete evidence before reopening access. Reconstructed audit projections preserve original event identities and mark their recovery provenance; they do not emit a second deletion success.

Task purge and principal/resource deletion cannot cascade away required receipts, member indexes or event attribution. Ordinary audit events may expire under their separate policy, but protected acknowledgements and minimum lookup evidence must remain discoverable for their promised lifetime. A missing, wrong-lineage, stale or unverifiable checkpoint is an explicit recovery gap. There is no claim of tamper-proof storage, arbitrary rollback detection, or removal from backups/WAL/external recipients outside the declared managed scope.

Safe sink projection and delivery¶

Build the sink projection from an allowlist before subscription templates, preview/test, delivery persistence or transport serialization. No template can recover the privileged audit document. The v1 sink view includes only the canonical event UUID, scoped operation/revision, coarse actor kind, event name, scope, committed outcome, bounded reason codes and this scope's counts. Use a fixed catalog summary; null names, actor/initiator principal details, task ID, request/correlation IDs, snapshots, authority details, membership links and physical destination/artifact references. An administrator's system subscription also receives the safe view. Privileged audit export is a separate explicit integration, not an implicit sink option.

The existing numeric audit row ID and occurrence time remain envelope metadata for compatibility. They are not counts, commit-order proofs or catch-up watermarks; consumers deduplicate with the event UUID.

The v1 fixed sink summary is Lifecycle state changed; consumers display the specific transition from the typed name. No source-generated free text crosses this boundary.

Collection subscription matching requires the event's direct stable collection scope. Do not use related-collection metadata to route lifecycle batches. Keep existing ReadAudit, ManageEventSubscription, sink grants, enabled state, configuration revision and scoped-token checks. At delivery admission recheck the subscription's current authority and sink grants, including retries; a revoked/disabled destination does not send. The already-admitted in-flight request can finish. Redaction is not a way to bypass revoked authority.

Reuse existing at-least-once delivery, bounded attempts/backoff, claim fencing, dead-letter inspection and manual retry. Dedupe by canonical event_id per subscription/consumer. Different scoped events have different IDs. Preserve operation revision and causation for out-of-order reconciliation, but promise neither globally ordered nor exactly-once delivery. Sink acknowledgement proves transport delivery only; it cannot complete a migration or erasure.

Bound fan-out using existing batch settings and one delivery per matching subscription/event. The following delivery policy and catch-up rules make overload and unavailable history explicit.

Bounded delivery and gap evidence¶

Before lifecycle subscriptions can activate, require one persisted, validated delivery policy revision with deployment and per-scope retained-row and reserved payload-byte ceilings, a subscription/gap-slot ceiling, and finite delivery/gap visibility windows. An unconfigured policy rejects lifecycle opt-in; it does not disable canonical audit writes. Configure these values explicitly and qualify them with #504's profiles before activation. Report their non-secret effective values through administrator diagnostics.

Reserve 8 KiB per stored safe envelope plus one retained-row reservation at fan-out admission. Check both scope and deployment budgets in the same transaction, with checked arithmetic and canonical lock ordering. Count queued, retryable, in-flight, succeeded and dead rows until their actual purge; merely reaching a terminal state does not release retained storage. Physical attempts use the existing separate concurrency/retry budgets. Lowering limits prevents new acquisitions while existing reservations drain. Disabled retention can exhaust delivery capacity, but cannot create an unbounded terminal-row store. Rendered transport bytes remain subject to the existing size/concurrency limits; any persisted rendered copy needs its own byte reservation before writing.

Reserve one fixed-size gap slot when accepting a lifecycle subscription, including space for its deletion tombstone until the advertised visibility deadline. If the slot allowance is exhausted, reject new opt-in rather than accepting a subscription whose delivery loss cannot be recorded. Coalesce omissions into one record per stable subscription UUID, across configuration changes; retain only bounded reasons, observation times, a monotonic revision and an optional count. Counts that cannot remain exact become null with count_accuracy=unknown. Do not retain an unbounded event-ID list or one gap record per configuration.

Fan-out atomically inserts each admitted delivery or advances its reserved gap record before marking the source event dispatched. A repeated fan-out of the same committed event cannot charge or count it twice. A missing gap write rolls back that fan-out decision; the source remains undispatched and retryable. Reuse the current retention protection for undispatched events rather than discarding them as notification failures. This is local persistence, never a wait for a sink acknowledgement, and does not make physical lifecycle completion depend on an external receiver. Required canonical audit persistence still fails closed. Exhaustion of required local audit/evidence capacity is an admission failure, with protected cleanup/recovery capacity retained; it cannot be hidden by dropping undispatched audit facts.

The delivery-status schema distinguishes configured capacity, an open/acknowledged gap, unknown counts and source-history loss. Its observation times bound recorded fan-out observations; they are not event-time intervals, commit watermarks or exact missing membership. gap=null means no retained gap record, not proof that every historical event was delivered. After gap visibility expires, keep an explicit expired/unknown history state until its subscription/tombstone can be retired within the slot budget. Dead-letter expiry can create a gap; acknowledgement does not erase that fact or prove consumption. New omissions reopen the record at a new revision.

Bounded catch-up and source retention¶

Catch-up creates a principal-owned, admitted export through existing task/query and artifact capabilities. Its input is a fixed set of currently committed, authorized lifecycle events captured in a short database snapshot under the subscription configuration and gap revision. Capture at most 10k candidates, 64 MiB input and 16 MiB encoded result, stopping before publication on any limit. The immutable result uses lifecycle-catchup-jsonl-v1: one safe sink envelope per UTF-8 JSON line, followed by LF, with no BOM. Each envelope retains its canonical event UUID. Encoded length and SHA-256 cover all bytes, including LFs; the existing verified output/download contract applies. The capture receipt binds that result, scope, configuration/gap revisions, readiness and availability window independently of the original task's remaining details.

Capture coverage is complete only for its captured_committed_set. It does not claim every event ever committed in a wall-clock interval, include later commits, prove delivery to a sink, or automatically close a gap. Late commits go through normal fan-out and may advance the gap revision; a later capture can include them. Reading the result or ending a client wait does not acknowledge a gap or cancel server work. An explicit authorized acknowledgement binds an expected gap revision and records operator awareness only. Stale acknowledgement conflicts; it cannot clear a newer omission, be labelled recovered, or acknowledge erasure. The request also binds the expected subscription configuration revision and opaque scoped source-retention generation from the status response. A concurrent configuration change or source purge therefore conflicts even without another omission. A successful acknowledgement advances the gap revision and records the reviewed prior revision separately; repeats of that settled acknowledgement are no-ops. Its audit-only canonical event carries the typed delivery references, not notification payloads or an external-receipt assertion. Recognize a matching retained acknowledgement receipt before the stale-state check; a changed actor/request cannot reuse it as a new acknowledgement.

Audit retention advances an authorization-scoped source-retention generation in the same transaction as its purge. A capture compares the retained configuration, gap and source-generation evidence; source expiry, lost configuration history or unsupported recovery coverage is reported as expired/unknown history. A captured set may still be readable after its source rows expire, subject to its own availability and current authorization/erasure, but it cannot become proof that the missing notification history was recovered. Holds and protected receipts keep their separate lifetimes. This closes the case where a sink outage outlives ordinary audit retention without silently extending that retention forever. Capture source_history and source_generation describe the assessment at captured_at; they are not a perpetual claim about the source. Delivery status assesses current source history. Neither view marks notification recovery from a historical assessment or a successful output download.

Logical restore and supported physical recovery bind this state to #511's verified application incarnation. Invalidate stale acknowledgement/capture continuations and establish a new scoped source generation before exposure. Unreconciled or lost notification history is unknown with recovery_gap, not quietly retained or recovered. Reuse the existing protected recovery authority; gap records are not another deletion ledger. Restoring a backup does not automatically resend notifications or prove what an external receiver retained.

Initially capture hot audit rows only. Archived event search/retrieval requires its separately qualified reader; discovery must report unsupported modes instead of silently omitting them. Preserve capture discovery through its advertised result window after reconnect or task-detail purge. An expired result is a typed expired outcome, never an empty successful export. Every inspection/download rechecks scope and current authority; unauthorized identity lookup returns the same 404 as an absent identity.

Retention and public API proposal¶

Evidence Lifetime and access
Canonical audit events Independent configured audit window, with ReadAudit; append-only except bounded authorized retention
Exact membership and resource/version index At least the promised event evidence window and any outstanding protected obligation; advertised expiry; no task cascade
Protected deletion receipts/checkpoints #511's recovery/restorable-copy horizon, independent of event/task retention; explicit minimum identity minimization rules

Keep the existing event retention defaults until a feature supplies qualified integration. Audit-data retention records one bounded evidence.expired summary per committed batch, with exact retention-batch identity and scoped counts; purging such summaries does not recursively emit another summary. Its durable retention completion receipt supplies idempotency/accounting. It is audit-only and does not delay on a sink. Protected evidence cannot be purged merely because its ordinary event or task expired.

The following additions are proposed routes and filters, not currently implemented API claims. Implement them with the owning feature, shared response helpers and ApiError; then add annotations and regenerate docs/openapi.json. The downloadable audit schema, sink schema, membership schema, unavailable-evidence schema, delivery-status schema, capture-receipt schema and shared examples define these views before rollout. Schemas validate structure; typed constructors must additionally enforce UUID relationships, member ordering/uniqueness, digest/count agreement, time ordering and proof authenticity. The examples are independent state samples, except the paired published audit/sink views and their complete membership page.

The producer schemas use Draft 7 so the repository validator asserts date-time formats, including real calendar dates. UUID patterns enforce canonical lowercase RFC identities, including version and variant constraints. Consumers must enable format validation; matching a timestamp's shape alone is insufficient. Legacy naive-UTC event occurrence timestamps still require typed calendar validation.

POST /api/v1/collections/{collection_id}/event-subscriptions/{subscription_id}/lifecycle-captures Validate current scope/configuration and admit an existing export/query task; return 202 with durable task and capture references. No outbound re-send is implied. The system variant remains administrator-only.
GET /api/v1/collections/{collection_id}/event-subscriptions/{subscription_id}/lifecycle-captures/{capture_uuid} Authorized capture receipt and verified output reference through the declared window, including after task details expire. Preserve typed expired/unavailable outcomes.
POST /api/v1/collections/{collection_id}/event-subscriptions/{subscription_id}/lifecycle-delivery-status/acknowledgements Expected-revision acknowledgement of gap awareness. Conflict on stale revision; no notification recovery, external receipt or lifecycle-completion claim.

The same suffixes on /api/v1/system-event-subscriptions/{subscription_id} require an unscoped administrator. Capture output uses its capture-specific /output route and the existing verified-download helpers, including after its original task disappears; it does not expose a generic provider/file API. Collection status exposes only authorized scope usage and limits. Deployment usage belongs in administrator diagnostics, not a partial-scope response.

Output owned by a capture must retain explicit authorization, retention and resource accounting ownership before task details retire. If an adapter cannot transfer that ownership, dependent task purge remains blocked. Task expiry cannot erase an available capture or refund bytes whose physical cleanup is still pending.

A fully available empty membership page means complete empty evidence. Expired, missing, minimized, corrupt, unsupported-format or dependency-incomplete evidence must not become an empty success. Known authorized expired evidence returns 410 with a typed bounded reason and safe receipt reference when retained; transient evidence unavailability returns 503; corrupt/dependency-incomplete evidence returns a typed failure without complete coverage. A nonexistent or unauthorized identity returns the same 404 shape. Never reveal expiry, counts or receipt links before authorization. A retained tombstone is needed to distinguish authorized expiry; once it expires, ordinary 404 is correct.

Readers preserve unknown optional fields/reasons and display unsupported names or major contract versions without claiming completion. Producers validate the closed v1 schemas and allowlists. Additive optional read fields do not authorize new outbound fields. A changed required meaning needs a new contract version and reviewed migration. Keep event names and evidence availability separate from task phase, SSE updates, metrics and consumer wait timeouts.

examples.json separates valid producer examples from reader_cases that deliberately extend the closed v1 grammar. The latter specify preservation or unsupported outcomes for consumer review. delivery_cases supplies actual duplicated/out-of-order safe envelopes, including a revision above JavaScript's exact-number range. Validating their structure does not prove a consumer's reconciliation or interpretation; its own tests must run those vectors. catchup-output.jsonl provides a complete two-event output with a matching capture-receipt digest and length. Delivery-status/capture examples include unconfigured capacity, saturated unknown counts, source expiry, stale task details and an acknowledged gap whose history remains unavailable.
