Task receipts and retention¶

Protected task receipts preserve submission deduplication after task details are removed. They apply to imports, backups, direct exports, template runs, remote target invocations and schema profiles submitted with an idempotency key.

Retry behavior¶

A receipt binds a stable principal UUID and a protected idempotency-key digest to the original request fingerprint, task UUID, kind and bounded outcome. It contains no request body, raw key, credentials, result body or output bytes. The independent repository key authenticates checkpoints and derives receipt digests in separate domains. Changing that key does not create a fresh namespace: an activated deployment rejects a mismatched or missing key.

New keyed tasks remain unclaimable until their exact admission generation has been independently protected. A duplicate consumes no new task capacity, credential approval or external effect. Matching retries return the existing task while its details are available. A changed request conflicts during the receipt window, even when dependencies have since changed or disappeared.

After details are removed, an authorized matching retry returns HTTP 410 with only the stable task UUID, kind, expiry and reason. The caller must still own the receipt and pass the selected authorization backend's task-read check. The response grants no old integer task location, output access or cancellation rights. External policy uses the resource identity receipt:<task UUID>.

The deduplication duration is captured at admission and anchored once at the first known terminal outcome. Retries and restore do not extend protected terminal deadlines; active work never expires merely because time has passed. Terminal anchors are independently protected before receipt retirement advances the monotonic expiry floor. Only then can a reused key create another generation. An old admission ticket cannot activate that generation.

HTTP outcomes and consumer actions¶

The same rules apply to keyed import, backup, export, template export, remote invocation and schema-profile submissions. Treat these as distinct outcomes:

  • HTTP 202 for a recognized request returns its existing task. Continue reading that task; do not assume the operation executed again.
  • HTTP 409 with reason: idempotency_key_conflict means the key still identifies a different protected request or kind. No new work was created. Do not replace the key automatically to get past the conflict.
  • HTTP 410 with reason: task_details_expired recognizes the original submission after its details were removed. No work or capacity reservation was created. Keep the receipt outcome; do not turn this response into a new submission.
  • After independently protected receipt retirement, normal admission can accept the key as a new generation and return HTTP 202 with a new task reference. That is new work with new effects. A client clock, HTTP 404, or HTTP 410 does not prove retirement or authorize it. Require an intentional new user request.

For example, a changed protected request returns:

HTTP/1.1 409 Conflict
Content-Type: application/json
Cache-Control: no-store

{"error":"Conflict","reason":"idempotency_key_conflict","message":"The idempotency key identifies a different protected request; no new work was created"}

A recognized submission with removed details returns:

HTTP/1.1 410 Gone
Content-Type: application/json
Cache-Control: no-store

{"error":"Gone","message":"Task details have expired; the original submission is still recognized; no new work was created","reason":"task_details_expired","task_identity":"00000000-0000-4000-8000-000000000001","kind":"export","expires_at":null}

Both responses preserve the standard error/message envelope so existing clients can explain the outcome without parsing prose. Neither response includes Retry-After. The receipt's expires_at is its deduplication deadline, when known; it is not a result-availability deadline or a promise that a later retry will be accepted. Preserve unknown optional response fields and handle unknown reasons using the HTTP status without parsing messages. Shared examples live in tests/fixtures/lifecycle/task_submission_outcomes.json. The server's HTTP tests exercise these examples for every keyed submission kind.

Task/result inspection still requires current authentication and permission. An authorized retained task can report an expired output as HTTP 410. A missing or already purged task/output returns HTTP 404; an unauthorized request follows the route's permission-safe denial behavior. Neither response grants output access, a different principal's receipt, or permission to submit new work. The existing output routes may use the general ApiErrorResponse shape for expiry; the submission receipt response above is a separate typed contract.

Upgrade and activation¶

Stop older API, worker, restore and administrator binaries. Apply migration 2026-10-31-000008_task_retention, reconcile database grants, and deploy matching binaries with the same independent control repository and authentication key. Keep these outside supported database rollback, following deletion recovery. The migration leaves receipt protection disabled until explicit activation; existing behavior remains available during this initial state.

Every command below requires --control-recovery-directory and --control-recovery-key, or their HUBUUM_CONTROL_RECOVERY_DIRECTORY and HUBUUM_CONTROL_RECOVERY_KEY environment variables. Initialize a new repository using the existing control-checkpoint bootstrap procedure before activation.

hubuum-admin --task-retention status
hubuum-admin --task-retention preview
hubuum-admin --task-retention enable --task-retention-confirmation '<preview confirmation>'

Review the preview before enabling: the first finite legacy deduplication window uses original terminal timestamps, so an old terminal receipt can become eligible for retirement immediately. The preview reports a bounded sample, not an exact whole-database count. Its confirmation binds the current authority and policy. Repeat enable while its report says more: true; each invocation handles a bounded backfill batch and protects its progress. New keyed submissions are unavailable during backfill. The final transition to protected operation requires all legacy candidates and pending acknowledgements to be resolved and the new activation checkpoint to be durably read back.

Backfill preserves original identity and clocks. It never reconstructs an unprovable original request from a redacted or expanded payload. Those legacy requests return a conflict rather than executing again during their window. Existing tasks are grandfathered out of detail expiry; activation does not silently apply a new deletion deadline to old details.

The default deduplication window is seven days after terminal completion; detail expiry is disabled. Policy changes affect subsequent admissions. An update compares the policy revision: concurrent receipt settlement does not invalidate it, while a competing policy edit requires reading the latest policy before retrying. Hold creation and release similarly compare the captured decision for that hold ID, preserving concurrent receipts and other holds. For example:

hubuum-admin --task-retention set-policy \
  --task-retention-deduplication-seconds 604800 \
  --task-retention-details-seconds 86400
hubuum-admin --task-retention run

Omitting --task-retention-details-seconds in set-policy disables detail expiry for subsequent admissions. The run command performs one bounded maintenance pass; normal workers continue eligible work automatically.

Holds, outputs and bounded cleanup¶

When another publisher holds the independent repository, background workers leave cleanup due and continue already admitted task work under the current application permit and task execution checks. Explicit cleanup commands return the retryable repository-busy refusal. Missing or changed keys, invalid evidence and filesystem failures remain errors. A deferred attempt performs no retention mutation or completion acknowledgement.

Each process with task execution enabled runs one maintenance loop alongside its configured task claimants. Cleanup retains its own application admission, maintenance/quarantine checks, execution scope and shutdown handling. Its local schedules avoid backend polling between cleanup intervals. A bounded pass can continue pending work without making a queue claimant wait for that pass; protected admission activation wakes the queue separately. Productive passes and repository-busy refusals retry after a 100 ms pause, or the configured worker poll interval if shorter. This gives other publishers time to acquire the repository without postponing known debt for an entire idle poll. Idle, blocked-only and failed passes retain the configured worker poll interval. Shutdown interrupts that wait. Artifact cleanup uses the same maintenance loop. Task visibility compares stable UUIDs directly against retained targets, and queue claims use an index matching their status, kind and creation order. Retained decisions therefore do not require a full target scan for each claim. Explicit administrator sweeps use the same protected cleanup service. Their reports describe the exact verified completion checkpoint, even when another publisher subsequently acquires the repository. Receipt expiry can reuse an existing checkpoint only if it covers the selected revision, exact generations and original terminal anchors; the post-expiry floor and removals still require independent publication.

Use stable UUIDs when retrying hold commands:

hubuum-admin --task-retention hold --task-hold-id '<hold UUID>' \
  --task-hold-task '<task UUID>' --task-hold-reason legal
hubuum-admin --task-retention release-hold --task-hold-id '<hold UUID>'

Holds can have a fixed --task-hold-expires-at timestamp; otherwise they remain until explicitly released. Released hold decisions remain in protected authority. Publishing their release is required before a previously protected purge may use that release. A new hold still blocks deletion immediately.

Cleanup protects an immutable manifest before deleting its selected scope and protects completion before acknowledging removal. One manifest contains at most 64 distinct task UUIDs. Each pass has an aggregate budget of 1,000 persisted rows and 16 MiB of measured row input, including owned children. Oversized indivisible rows block explicitly. Held or blocked targets do not prevent progress on other eligible targets.

One pass can prepare and process up to eight fixed manifests under that shared budget. It publishes their intents together and protects all completed removals before returning acknowledgement. Interrupted completion publication is repaired at the start of the next pass. Receipt retirement uses a separate batch of up to 1,000 metadata references, with exact terminal-anchor checks and a protected expiry floor; it does not inherit the 64-task physical manifest limit.

Detail cleanup preserves available outputs, repair reports without an expiry, active dependencies and required provenance. Expired export, backup and profile outputs use a separate manifest scope, so their cleanup does not depend on detail expiry. Global audit records retain captured stable task identities even after a task row is removed. Scoped task reads disappear when their purge intent becomes effective. Reads already started under an earlier database snapshot may finish; retention cannot retract bytes already delivered.

Published task-owned artifact chunks, manifests and reservations participate in the protected purge. Their independent verification digest preserves this requirement after an output reference or its original task disappears. Each physical row consumes the same batch row/byte budget. Reservations remain charged through the local producer cleanup grace and until the physical obligation has been retired. A removed output catalog row alone is not evidence that its bytes are gone. An abandoned unpublished attempt becomes eligible once its task is terminal; it does not wait for a result-availability window that never began. Unpublished staging also retains its existing lease-fenced cleanup path, so an abandoned attempt can release capacity during a retry. Both adapters pin current holds before that cleanup; a hold still prevents removal.

Result availability and reconnecting¶

Existing task discovery is principal-owned rather than session-owned. After re-authentication, list /api/v1/tasks with the appropriate kind/status filters and use the returned links. Closing a browser or local wait does not cancel the task. Each later read checks current authorization again.

For new export and backup results, the configured output lifetime starts at atomic successful completion. Preparation time does not consume that window. Configure HUBUUM_EXPORT_OUTPUT_RETENTION_HOURS=48 and HUBUUM_BACKUP_OUTPUT_RETENTION_HOURS=48 for a two-day post-ready window. The terminal task's finished_at is the ready-time anchor; details.export.output_expires_at or details.backup.output_expires_at is the availability deadline. Detail cleanup preserves discovery while an output is available, even if its detail policy would otherwise expire sooner. Receipt deduplication has its own independently protected window.

Restoring a recorded result preserves its original deadline. Retrieval does not extend source-version retention or override erasure, holds, or current authorization. This change covers existing export/backup results; warm/cold retrieval workflows and their full cross-login, next-day acceptance are owned by the coordinated #545, #516 and #517 contracts.

Receipt authority has independent limits of 16,384 records and 12 MiB. Admission reserves each record's worst-case terminal growth, so the byte limit can be reached before the count limit. Each receipt must fit 1,024 encoded bytes. Retention authority has a separate 4 MiB limit, at most 1,024 manifests, 64 policy revisions and 1,024 retained hold decisions. These are safety limits, not promises that all maximum populations fit simultaneously. Capacity exhaustion refuses new protected work instead of discarding applicable obligations.

Recovery and retained evidence¶

The signed checkpoint contains independent deletion and task-control revisions. Ordinary admission, terminal settlement and retention advance task authority without invalidating unrelated application's deletion fences. A checkpoint keeps the latest complete state; it is not an unbounded operation log.

After physical recovery, --recover-control restores compatible authority while leaving the application quarantined. --reapply-control settles old nonterminal tasks and orphaned unresolved receipts as recovery-unknown, establishes their fixed settlement anchor, reapplies retained output/detail purges, independently protects the exact completion and only then releases the recovered incarnation. Logical restore preserves authority and follows the same reapplication rules. A prior removal receipt is never proof that an older restored copy is absent.

Backups predating stable task and principal identities can synthesize new UUIDs on restore. Such derived identities cannot prove that an old purge target is absent or that an old receipt belongs to a different person. With retained purge decisions or receipt ownership, unresolved correspondence keeps recovery quarantined. Use a backup carrying matching stable identity evidence; removing the independent evidence would discard the promised recovery protection.

The repository retains the current checkpoint and its predecessor. It collects only authenticated superseded files after durable latest-reference readback. Unknown, conflicting and unrelated partial files consume capacity and are not silently removed. Publication may complete an interrupted candidate only when its existing contents are the exact prefix of the expected unpublished bytes. Repository entry and byte caps include staged files and temporary references.

Checkpoint metrics use bounded operation labels and include actual encoded and verified work, file reads/writes, synchronization, collection and lock contention. Set HUBUUM_CONTROL_CHECKPOINT_MEASURE=true to include a cumulative checkpoint_measurement object in administrator retention reports. It measures this administrator process only and changes no lifecycle behavior; aggregate separate invocations explicitly when measuring a multi-command operation.

Purge decisions and hold releases currently remain for the full lineage. This does not erase other backups, WAL, artifacts outside the selected scope or prior downloads. Receipts keep sensitive matching fields in explicit bounded records for a later authorized targeted-erasure operation; retention alone does not claim that separate erasure capability.

Scheduler integration¶

Concurrent protected admissions share one verified publication session for at most 32 requests from the same storage handle. A smaller waiting group has a 10 ms coalescing window before acquiring the independent publication lock, giving concurrent database reservations time to join. Full waiting groups proceed immediately. Light traffic can therefore incur up to 10 ms of deliberate batching delay; no protection deadline is renewed. Their exact-ticket activations may overlap while that session stays locked. PostgreSQL activation holds shared deletion and retention authority locks through its transaction, plus the exact task row lock. Receipt changes, retention policy/hold changes and recovery retain exclusive authority locks, so concurrency does not weaken the generation fence. Before returning HTTP 503 for a busy repository, an admission batch waits up to one second to acquire the cross-replica publication lock. Each attempt reopens the repository and checks its key; an acquired session verifies current recovery evidence. Authentication and recovery failures still fail immediately. Waiting does not renew a task deadline or authorize execution without its exact proof. The bounded group is selected after session acquisition, so requests arriving during lock contention or verification can share that session. When the oldest waiting requests are already captured, their contiguous queue prefix activates without republishing for newer uncaptured requests. The first uncaptured request keeps its queue position; later protected requests cannot overtake it indefinitely. PostgreSQL builds complete snapshots as JSON text for direct decoding into validated domain types; stored receipt and authority records remain JSONB. The publisher can reuse the exact immutable payload it just signed and read back; every session still checks the independent files, authenticated HEAD, digest, key and durability afresh. At most three authenticated decodings are retained per configured receipt service, covering the current, previous and collectible checkpoint. Collection also reads and checks the actual file and signing key before reuse, charges the same byte budget, and independently checks that the current checkpoint supersedes the candidate. Missing, changed or unauthenticated files cannot be collected by consulting the cache alone.

Protected receipt and detail maintenance runs at the configured task-worker poll interval, including after an idle pass. It does not inherit the legacy output cleanup interval (300 seconds by default). Each pass still releases publication ownership; productive or contended passes use the shorter publisher pause. Its row, byte and manifest bounds remain in effect. Legacy output and artifact cleanup retain their configured interval.

Receipt activation and task visibility are checked while choosing each queue head, before scheduling counters or worker leases advance. A pending receipt, retained purge restriction or unavailable recovery binding cannot execute or block an eligible task behind it. Memory and PostgreSQL retain this behavior for ordinary selection and overdue promotion.

This layer advances the SDK train from scheduling's 0.15 to 0.16. Upgrade all ten SDK crates together and implement the complete retention and combined recovery proof contracts. The earlier scheduler P3/P4 report measures the source before retention; it does not qualify retention's additional receipt checks. P6 remains a separate open acceptance gate.
